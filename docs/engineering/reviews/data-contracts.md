# Proposed relational and transaction contracts

Status: **PLANNED**. This is a technical proposal supporting [readiness findings](architecture-readiness.md), not executable schema or a replacement for approved product decisions. Q01/Q03/Q07/Q08 must be resolved before dependent migrations. Preserve ADRs 0005/0007/0008/0009. Schema files will belong to the API database layer; generated forward-only SQL and Drizzle metadata belong under `db/migrations/`.

## Common conventions

- UUID primary keys for independently addressed entities; composite keys for simple joins. `created_at` and `updated_at` are `timestamptz NOT NULL`, server-generated. Update timestamps must be maintained explicitly, not assumed from a database default. Use revisions for Focus whole-list replacement and optimistic Skills writes only. Ordinary record/profile CRUD uses atomic last-committed-write behavior; no blanket revision convention.
- Closed enums: role, catalog scope, skill origin/category/proficiency, employment type, education status. Define one mapping between GraphQL and database values. Source types begin MANUAL/WORK_EXPERIENCE/EDUCATION/CERTIFICATION; future imports require a reviewed additive migration. Do not populate speculative RECOMMENDATION/ASSESSMENT rows now.
- Preserve display labels. Proposed normalized key: NFKC, trim, collapse whitespace, consistent case normalization; preserve punctuation/diacritics in identity keys until Q08 resolves equivalences. Search may have a separate folded key. Never collapse C, C++ and C#. Version the normalizer and use the same fixtures for seeds and writes. Email normalization is separate; do not strip provider-specific dots or plus suffixes.
- Every private definition has an owner FK; `GLOBAL => owner IS NULL`, `USER => owner IS NOT NULL`. Skills express the corresponding invariant with `origin CATALOG/CUSTOM`, not an extra competing boolean. Global normalized uniqueness and per-owner normalized uniqueness require distinct partial indexes; one nullable-owner unique key would allow duplicates. Certification definition uniqueness also includes board.
- A private definition/association can reference global rows or its own owner's private rows, never another user's. A global association can reference only global definitions. Validate in services and enforce cross-table invariants using composite references where expressible, otherwise select a narrowly scoped constraint trigger only for the concrete cross-row invariant that a FK cannot express. Do not build a generic trigger-generation framework. PostgreSQL CHECK cannot validate arbitrary other-row data. [PostgreSQL constraints](https://www.postgresql.org/docs/16/ddl-constraints.html)
- Published global catalog rows are not user-editable; referenced definition deletion is RESTRICT. Prefer retiring catalog entries later over deleting referenced history, but do not invent an active/archive product feature now. Custom rows are retained for owner reuse after record removal; canceled form drafts create no rows. An explicit future cleanup can delete unreferenced private definitions.
- FK indexes are deliberate: index owner/user references and reverse lookups used for reconciliation. Use normalized B-tree indexes for equality/unique keys, pg_trgm GIN on measured large search columns, and parent-first relation indexes. Do not add both GIN and GiST to every small catalog by default.

## Derived-skill extension contract

The separation of definition, user association and source link is required now. Keep the first migration MANUAL-only; each source-domain migration adds a nullable typed FK, exact source-shape check and partial unique `(user_skill_id, source_record_id)` index. Reference the saved Work/Education/Certification record, never its catalog title/program/board: two records of one type can independently support one skill. A later Resume import adds a durable import-record FK through an additive migration; arbitrary polymorphic IDs and a generic source registry are unnecessary.

Serialize every skill-affecting transaction on the owning `users` row **before** creating or reading associations for reconciliation. This also handles the absent-association race without advisory locks or a per-source lock protocol. Keep the lock through the source record and source-link commit; different users remain independent. Preserve lock ordering with auth/reset checks and do all expensive/non-DB work before locking.

Source edits diff the persisted links for that exact record against the approved mapped skill IDs. Keep unchanged links, add missing ones automatically and idempotently, and remove only obsolete links from that record. Attaching another source preserves existing proficiency and MANUAL links; removing the final link deletes the orphaned user-skill association and any dismissal. Catalog definitions are never deleted as a side effect. Stored links are the historical contribution: changing seed mappings alone must not silently recalculate every profile. A bulk remap/backfill is separate reviewed work, not an initial-release job system.

Required tests in 05C/06C/07C: same-type records A+B contribute one skill; mapped skills attach without confirmation; editing A from skill X to Y retains B/MANUAL support for X; replaying a save creates no duplicate source; a dismissed skill remains hidden after a source edit; deletion of the last source removes the association and dismissal; source-save failure rolls back catalog/record/links; competing manual-add and source-delete cannot drop a supported association. Add cross-type combinations as each real domain arrives. No generic reconciliation engine before two concrete derived consumers.

Q02 is resolved: `×` dismisses a derived-supported skill from the Skills projection using separate dismissal storage; source saves preserve that dismissal. Re-adding the skill clears dismissal and restores a MANUAL source. Reviewed mappings attach automatically, and the final-source deletion removes the association and dismissal. Do not add a suggestion-approval workflow or alternate retention policy.

## Account state machine

Authentication, setup, and onboarding are independent. No session means anonymous. Valid setup grant permits password establishment only. Valid session with incomplete onboarding permits viewer/profile/onboarding-domain operations but not normal routes; server completion checks required fields. Completed onboarding opens normal self-service routes. ADMIN authorization remains a separate role check. A reset increments credential generation, removes password, marks setup required and invalidates sessions without changing onboarding completion.

Registration creates USER plus its initial profile row and session atomically. The profile row may initially contain only `user_id`; Phase 02 adds fields with a migration for existing users. Login must not issue a session from a password verified against a superseded credential generation. Lock/recheck generation after hashing verification; hash work itself need not hold a long database lock. Session validation checks current generation. Q01 determines safe proof delivery, never email alone.

## Transaction matrix

| Workflow | One transaction / locking | Failure and retry contract |
| --- | --- | --- |
| Public registration | normalized email uniqueness; create USER, base profile, session | No partial account/session; duplicate normalized email stable error; client preserves input without logging password. |
| Admin creation | role authorization; create requested role, incomplete profile, setup state/grant and audit event | Grant secret returned once via approved channel, never persisted raw. Duplicate email rolls back whole creation. |
| Set password / reset | lock user; validate/consume grant or authorize admin; compare generation; credential/session/grant/audit changes | Replayed/expired token rejected; concurrent reset wins by generation recheck; onboarding untouched. |
| Custom selection + record | validate visible IDs; exact-visible reuse; private row upsert; private relation; record; source reconciliation | Unique conflict reloads canonical row in transaction/savepoint; do not retry an aborted PostgreSQL transaction in place. Cancel never opens transaction. |
| Custom skill + manual association | classify approved label; definition resolution; unique user_skill; MANUAL source | Concurrent attempts cannot duplicate definition/association; atomic duplicate result/error as contract specifies. |
| Source update/delete | lock owning user first for every skill-affecting write, including manual add/move/remove and source save/delete; replace only that source record's links and reconcile remaining sources | Recheck sources under lock; attaching and removing from different sources cannot delete a supported skill. No remote provider call inside transaction. |
| Skill remove/move | lock owning user, then check revision where optimistic proficiency writes require it; remove manual-only association or persist derived dismissal, or update proficiency | Return canonical removed/dismissed outcome or conflict; same-skill writes serialize; unrelated skills unaffected. |
| Focus save | lock user/check focus revision; resolve custom definitions; delete and insert ordered association set; update revision | Stale revision -> CONFLICT; no accidental primary auto-selection; entire list restored/refetched on failure. |
| Onboarding completion | lock user first, then profile; validate required fields from saved state; stamp completion once | Idempotent completion; client cannot supply timestamp or bypass requirements. |

## Deletion and future user purge

Account deletion is explicitly outside current product scope; do not add an endpoint. Nevertheless define the FK topology now: sessions/grants/profile/records/user associations cascade from user; source links disappear before unreferenced skill relationships; private catalog definitions/relations can be removed only after owned records/associations. Global catalog definitions survive user deletion. Use an ordered maintenance transaction for future purge if RESTRICT references prevent a simple cascade. Review FK reachability now; defer a full purge procedure and its integration tests until account deletion is actually in scope.

## Dates, normalization and indexes: migration gates

Q07 should select either true month keys (`YYYY-MM`, persisted as year/month or an integer month ordinal) or a precisely documented canonical SQL date representing a month. Do not silently imply day precision by inserting day 1. DOB uses a calendar date and no timezone conversion. Dynamic “DOB not in future” validation belongs in the service; avoid volatile time-dependent CHECK assumptions.

Q08 must approve exact identity normalization before seed imports. Benchmark top-N ranking against fixture and enlarged catalogs with `EXPLAIN (ANALYZE, BUFFERS)`, including short queries, `%`/`_` escaping, unrelated private records and parent filters. Apply trigram thresholds deliberately; do not sort all rows on each keystroke. Admin indexes follow chosen sort/filter combinations, not every Cartesian combination. Empty DB migration, second migration run and two seed runs are required evidence in each database phase.
